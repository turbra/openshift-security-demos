Technical details and enforcement checks

This operating model combines approved requests with configured authorization and network controls. Approver titles represent responsibilities to assign within the organization. Every route that creates a project, grants access, or deploys an application must enforce the same intended boundaries.

Provision the baseline on every creation path

The project request records the application, accountable owner, environment, and required connectivity. Application teams cannot self-provision; an approved platform workflow creates the project and verifies its baseline before releasing it for use.

OpenShift can include NetworkPolicy objects in its project request template. That template applies to the project-request path. Automation that directly creates a Namespace or Project must explicitly apply and verify the same centrally maintained baseline.

The baseline selects the intended application pods for ingress and egress isolation. Add only the required application flows and platform dependencies, such as ingress-router traffic and DNS where needed. Verify the policy coverage for the workload’s network configuration.

Keep mandatory controls effective

A template supplies initial configuration. Continued enforcement needs controls outside application-team edit rights. NetworkPolicies are additive: protecting one default-deny object against deletion does not stop a broader allow policy from widening access.

In production, restrict policy and RBAC changes to approved platform paths, and validate submitted workloads and allowed runtime identities. Where a mandatory network boundary must also hold for project admins, use suitable administrator-controlled network rules or verified admission restrictions. Appropriately scoped AdminNetworkPolicy deny rules can provide an administrator-owned boundary; BaselineAdminNetworkPolicy is fallback behavior and may be overridden by tenant NetworkPolicy.

Grant access by environment

The user requests named projects, the environment, the required role, and a business reason. The application or environment owner approves the access; controlled identity management and role-binding automation apply it. Review effective permissions, including group memberships and additive grants.

Development project admin may be justified, but it can permit direct workload deployment and NetworkPolicy changes, subject to applicable admission and security controls. CI/CD-only remains a process requirement unless additional controls enforce it.

Application teams do not receive project admin in production. Define specific visibility and operational access. Review sensitive capabilities such as exec, workload changes, and credential access individually; an operational role must not reopen the direct deployment path.

Curate the deployment identities

Developers submit source changes for code review. CI/CD builds, tests, and deploys to development. A designated production release owner approves promotion of the tested artifact. GitLab runners and GitLab with Ansible Automation Platform are alternative execution paths for this approved workflow.

The platform team approves separate development and production deployment service accounts. Limit each to the required API operations, resource types, and target project. Grant access to deployment credentials only to the protected automation path. Protect pipeline definitions, production approval gates, and the credential use path.

RBAC and admission must together prevent an otherwise permitted deployment from selecting an unapproved privileged runtime identity, changing permissions, or weakening mandatory policies. Giving the pipeline a different account name is not sufficient.

Separate deployment from application runtime

The deployment identity applies the approved workload configuration. The application runs as a different service account with purpose-specific permissions. Runtime authority comes from the application’s own role bindings; it does not inherit the deployer’s API permissions.

Where the application does not need Kubernetes API access, avoid granting unnecessary permissions or mounting an API token. Review each environment’s service accounts and their effective access independently.

Keep the approved-user boundary secure

Approval makes the required project available to an authorized user. Secure operator behavior is still required inside that project. Privileged automation must constrain requests to its intended targets and effects, including when the requester cannot perform the underlying operation directly.

Restricting project creation reduces who can establish a new project. It does not revoke existing project access or repair a vulnerable operator. Validate this operating model using an ordinary approved user after the project and its intended access have been granted.
