How the traffic and policies work · Technical details and example policy

This page animates a conceptual comparison. It does not connect to a cluster, run an exploit, or perform a network scan. Both applications have the same vulnerability and permissions. Only the application network policy changes.

What the animation represents

  • Routine application traffic: the attacker first makes an ordinary HTTPS request to the ingress router, which terminates TLS and forwards the request to the website. The website calls the application service through an allowed connection. Response packets follow the reverse direction of those allowed connections.
  • Application compromise: a malicious application request reaches the website on its permitted application port. Code execution remains possible on both sides.
  • Lateral access: the compromised application initiates a new TCP connection to the mock internal service. The left-hand service responds. On the right, the source application's egress policy drops the attempt before it reaches that service.
  • Required connections: the website and its approved connection to the application service remain available. The application remains compromised.

Scope of this example

The example selects the application pod on the default OpenShift pod network. It allows ingress from the router and egress to the application service pod in the same namespace. The application service and internal target accept the demonstrated connections; no other policy overrides the comparison.

NetworkPolicy rules are additive. Existing NetworkPolicies and administrator policies can change the result. Policies govern selected workloads, not an imaginary firewall at a namespace border. The effect of a policy change on existing connections is implementation-dependent; this example uses new connections.

The model uses numeric addresses for its backend connections. DNS and other infrastructure exceptions are omitted. Real deployments must explicitly allow their required dependencies. Host-network and local-node behavior also require separate consideration.

A VM can use the same approach when connected through its launcher pod on the default pod network with masquerade binding. Additional network interfaces need their own supported policy design.

The blocked attempt demonstrates network containment for the illustrated path. The application still has access to its own data and permitted connections. Reaching the mock service on the left does not imply that service was also compromised.

Policy for the application on the right

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: web-approved-connections
  namespace: demo-contained
spec:
  podSelector:
    matchLabels:
      app: vulnerable-web
  policyTypes:
    - Ingress
    - Egress
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              policy-group.network.openshift.io/ingress: ""
          podSelector: {}
      ports:
        - protocol: TCP
          port: 8080
  egress:
    - to:
        - podSelector:
            matchLabels:
              app: application-service
      ports:
        - protocol: TCP
          port: 8080

The example uses app: vulnerable-web for the website and app: application-service for its allowed dependency. Both listen on TCP 8080; the router terminates the external HTTPS connection. An egress podSelector without a namespace selector selects pods in this policy's namespace. Unlisted new connections are denied unless another applicable policy allows them. Return traffic for allowed connections is permitted implicitly.
